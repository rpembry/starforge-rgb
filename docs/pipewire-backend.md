# Opt-in PipeWire playback backend (uncommissioned)

`starforge_cues.pipewire_backend.PipeWireBackend` is a Fedora/PipeWire host adapter. Importing it and running the tests do not play audio. It is not wired into the CLI or a service. No live playback or device acceptance test has been performed.

The host must choose one exact PipeWire `Audio/Sink` node name and provide it to `AudioAdapter`. At each start, the backend resolves that name to one current node serial, starts one owned `pw-play` child targeting that serial, and waits to observe its uniquely named stream linked exclusively to the chosen sink. Its stream properties pin `target.object` to that serial and request `node.dont-fallback`, `node.dont-move`, and `node.dont-reconnect`. The backend checks those properties in the graph before feeding validated raw PCM. It checks the exclusive link before and after each PCM write and again after feeding completes. On a detected mismatch it stops the owned child and reports `unknown` because queued samples may already have sounded. The command uses `--volume` for per-stream gain (default and normal ceiling 0.05), `--sample-count` for finite playback, and a 20 ms requested latency. It never calls a system-volume control. If the sink is absent or ambiguous, or the link cannot be confirmed, it sends no PCM.

For an explicitly operator-selected, one-off commissioning gain above 0.05, both `AudioAdapter` and `PipeWireBackend` must be constructed with `commissioning_override=True`, and the adapter must receive the desired `gain`. The hard ceiling is 0.15 at both boundaries; no setting is persisted. Merely enabling one side cannot raise the other side's ceiling. This opt-in does not authorize playback: the operator still needs approval for the exact sink and test parameters. The validated WAV duration and size limits remain unchanged.

The adapter never starts a second voice while the backend has an uncertain owned process. A stop or lost acknowledgment triggers bounded terminate/kill/reap handling, then requires two spaced PipeWire graph snapshots without the owned node or its observed link. A failed process or graph check leaves the result `unknown` and blocks replacement. Elapsed clip time alone never clears uncertainty for this backend. `pw-play` does not offer a verified fade interface here; stop terminates the child promptly instead of claiming a fade.

These checks establish process and graph quiescence, **not physical silence**. PipeWire or device buffers may contain a tail after the owned link disappears. The graph may change between snapshots and between a check and a write. Stream routing controls are documented for the installed PipeWire 1.6.9 and WirePlumber 0.5.18, but their live behavior with `pw-play` has not been tested here. Live commissioning must verify the exact command, graph behavior, latency, and audible result at user-approved sink and gain. A future design needing a stronger no-overlap guarantee requires an audio engine with explicit drain/stop acknowledgment; this adapter should remain fail-closed where that cannot be established.

The fake tests inject graph snapshots, fake processes, and a fake PCM feeder. They cover exact target and per-stream gain, absence or wrong target, link change before or after feed, an unexpected extra link, missing routing properties, lost acknowledgment, time passing without positive quiescence, stop timeout, and independent RGB progress. They never execute `pw-play`.

References: [PipeWire `pw-cat` options](https://docs.pipewire.org/page_man_pw-cat_1.html), [PipeWire session manager properties](https://docs.pipewire.org/page_man_pipewire-props_7.html), and [WirePlumber 0.5 linking policy](https://pipewire.pages.freedesktop.org/wireplumber/policies/linking.html).

# Opt-in PipeWire playback backend (uncommissioned)

`starforge_cues.pipewire_backend.PipeWireBackend` is a Fedora/PipeWire host adapter. Importing it and running the tests do not play audio. It is not wired into the CLI or a service. No live playback or device acceptance test has been performed.

The host must choose one exact PipeWire `Audio/Sink` node name and provide it to `AudioAdapter`. At each start, the backend resolves that name to one current node serial, starts one owned `pw-play` child targeting that serial, and waits to observe its uniquely named stream linked exclusively to the chosen sink. Only then does it feed validated raw PCM from the bounded WAV asset. The command uses `--volume` for per-stream gain (at most 0.05), `--sample-count` for finite playback, and a 20 ms requested latency. It never calls a system-volume control. If the sink is absent or ambiguous, or the link cannot be confirmed, it sends no PCM.

The adapter never starts a second voice while the backend has an uncertain owned process. A stop or lost acknowledgment triggers bounded terminate/kill/reap handling, then requires two spaced PipeWire graph snapshots without the owned node or its observed link. A failed process or graph check leaves the result `unknown` and blocks replacement. Elapsed clip time alone never clears uncertainty for this backend. `pw-play` does not offer a verified fade interface here; stop terminates the child promptly instead of claiming a fade.

These checks establish process and graph quiescence, **not physical silence**. PipeWire or device buffers may contain a tail after the owned link disappears. The graph may change between snapshots. The pre-feed link check does not prove that every later frame reaches the selected hardware. Live commissioning must verify the exact command, graph behavior, latency, and audible result at user-approved sink and gain. A future design needing a stronger no-overlap guarantee requires an audio engine with explicit drain/stop acknowledgment; this adapter should remain fail-closed where that cannot be established.

The fake tests inject graph snapshots, fake processes, and a fake PCM feeder. They cover exact target and per-stream gain, absence or wrong target, link change before feed, lost acknowledgment, time passing without positive quiescence, stop timeout, and independent RGB progress. They never execute `pw-play`.

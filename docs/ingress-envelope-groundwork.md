# Ingress and protocol data groundwork (#53, #63)

`ingress_contract` defines host-owned `IngressBinding`, strict proposed `publish` / `retract` / `hello` frame values, and an authorization check that carries the binding ID forward. Binding scope limits source IDs, statuses, severity, confidence, text, subjects and retraction. The pure frame parser accepts a mapping with `proto: 1`; it does not change the existing bare-event Unix socket or authenticate its peer. A transport adapter must establish the binding from protected host configuration and local peer/listener context before these checks are a security boundary. No token is accepted from a producer frame.

`GenerationRef` and `GenerationIds` define a process epoch plus bounded monotonic ordinal distinct from reusable source/subject names. The host must create a fresh unpredictable 128-bit epoch at process start and allocate under the coordinator lock. `AdmittedTransition` carries generation, revision, event ID and semantic status for exact matching before future audio dispatch. These types are not yet wired into `LeaseBook`, the selector or the socket; the current producer v1 event and receipts remain unchanged.

The proposed envelope is strict within its version. A `retract` request carries source, subject, request ID and an **expected host-issued generation reference**. The caller's binding must own that exact current generation; an old request cannot retract a new run that reused the same source/subject name. The future publish/hello receipt must return the generation reference through a caller-private path before retraction can be used. A binding cannot offer retraction without subject support. A `hello` response should expose only that binding's allowed capabilities.

Request IDs are deduplicated under `(binding_id, request_id)` for ten monotonic minutes with at most 256 live records per binding and 4,096 globally. Under one host lock, first authenticate the caller binding and check its static frame scope. Next classify its request ID: an exact normalized retry is `duplicate` even if a successful first retract removed ownership; changed content under that ID is `conflict`. Only for a new ID, verify current binding ownership and expected generation, reserve the request record, then retract before releasing the lock. If retraction does not execute, roll back that new reservation under the same lock; an exact retry after a successful retract stays a duplicate. At capacity, reject with explicit backpressure; never evict a live request record to admit another. Expired request IDs need no permanent registry: a delayed request still fails the expected-generation check if its old run was replaced. The pure replay helper does not persist outcomes or perform retraction.

The current `status: cancelled` v1 event remains a compatibility path until #63 defines version dispatch and migration tests. It carries no expected generation and must not be enabled for less-trusted external producers that can race subject reuse. Byte limits, duplicate JSON-key rejection, local peer checks, status cursor authentication and a mandatory host registry are future integration gates, not properties of this pure mapping parser. No service or producer is activated here.

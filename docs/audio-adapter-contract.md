# Bounded audio adapter contract (issue #8 slice)

This slice adds a fake-tested audio sink and an injectable backend protocol. It does **not** contain or invoke a real playback backend, select a real output, change system volume, play sound, install a service, or enable background listening. The portable coordinator remains the sole policy owner; its audio channel independently reports accepted, unsupported, failed, suppressed or unknown. Adapter acceptance never proves that sound was heard.

`AudioAdapter` requires one exact host-selected sink ID. On every cue it verifies that this ID is available; it never substitutes the system default or another sink. Cue IDs map to validated local PCM WAV clips. `load_audio_clips` freshly validates the data-only theme manifest, asset path, digest and license/provenance metadata before decoding the mapped assets. An original two-note 500 ms test earcon can be generated in memory using only Python standard-library code. No theme script or URL is executed or fetched.

The hard bounds in this slice are at most 16 clips, 8 MiB total clip bytes, 1 MiB per WAV, mono/stereo 16-bit PCM at 8–48 kHz, at most 500 ms per clip, and 5% per-playback gain. One voice may be active. A new cue requests a 50 ms stop/fade for the previous one before starting; cancellation, expiry, quiet/mute clear and older-lease restoration stop rather than replaying prior audio. There is no audio queue, so stale sounds cannot be played later. Start failures remain isolated from RGB/text. An ambiguous start is not automatically retried; without a stop token, the adapter waits through the bounded clip duration before considering a new cue. A failed clear may be retried only under the coordinator's existing bounded clear policy.

The backend protocol has `available_sinks`, `start` and `stop` calls. The included fake backend records only selected sink ID, digest, gain, stop token and fade request, without playing bytes. A later real Fedora backend must prove explicit sink binding, bounded decoding and resource use, no fallback, stop/fade behavior, and precise outcome mapping before any manual playback. A manual test additionally needs a user-selected physical output and acceptable short-cue level/duration; system volume must remain unchanged. Actual heard results belong to the separate commissioning gate in issue #12.
